CASE STUDY

Cloud-Native DevOps Platform

In progress

An in-progress cloud platform with a Terraform-managed AWS network, an ASP.NET Core app, and an automated ECS Fargate deployment.

Problem

Build a repeatable path from application changes to a running AWS workload, while learning how infrastructure, identity, security, and health checks fit together.

Approach

Terraform provisions the network, ECR, load balancer, and ECS resources. GitHub Actions authenticates through OIDC, builds and publishes a commit-tagged image, deploys it to ECS, and checks service health.

Architecture

  1. Git commit
  2. GitHub Actions
  3. OIDC + IAM
  4. Docker image
  5. Amazon ECR
  6. ECS Fargate
  7. Application Load Balancer

Security

The workflow uses GitHub OIDC instead of long-lived AWS keys, scoped IAM permissions, separate ALB and ECS security groups, and ECR image scanning. The repository notes that the public load balancer currently uses HTTP; TLS remains planned.

Implemented

  • ASP.NET Core MVC application and automated tests
  • Docker image build and Amazon ECR publishing
  • Terraform-managed VPC, subnets, routing, security groups, ECR, ALB, and ECS Fargate
  • GitHub Actions deployment using OIDC and a least-privilege IAM role
  • Deployment health verification behind the ALB
  • Input validation, anti-forgery protection, and tested HTTP security headers

Planned

  • Production database configuration for PostgreSQL-backed request storage
  • Environment-aware deployments
  • AWS WAF and further application security
  • Kubernetes / Amazon EKS exploration
  • Prometheus, Grafana, and fuller observability

Evidence

The repository README records a successful CI/CD deployment, a healthy ALB target, and HTTP 200 from the public application. PostgreSQL persistence is verified locally; its production configuration is deferred. These are repository-reported results, not independent measurements.

Lessons

Using OIDC avoids storing long-lived AWS keys in GitHub. Separating liveness from database-aware readiness also makes health checks useful when database-backed changes are not yet configured for deployment.

Technologies
